# py-bumpver-release-action (by markcallen)

Reusable GitHub workflow for Python projects that:

1. Bumps version in `pyproject.toml` using bumpver
2. Commits & tags
3. Pushes changes
4. Creates a GitHub Release
5. Optionally generates release notes using AI via `everydaydevopsio/castoff/castoff`
6. Optionally records the release in `CHANGELOG.md`

If AI is disabled or fails, it falls back to GitHub autogenerated release notes.

## Usage from a project repo

GitHub resolves a reusable workflow only at `.github/workflows/` in the root of
a repository — subdirectories are not supported — so the copy in this
repository cannot be called from its path under `examples/`. Copy
`bumpver-release.yml` into the `.github/workflows/` directory of your own
project (or of a shared workflows repository), tag it, and call that copy. The
snippets below use `your-org/release-workflows@v1` as a stand-in for wherever
you put it; a copy in the same repository is called as
`./.github/workflows/bumpver-release.yml`.

```yaml
name: Release

on:
  workflow_dispatch:
    inputs:
      level:
        type: choice
        options: [patch, minor, major]
        default: patch
      use_ai_release_notes:
        type: boolean
        default: false
      update_changelog:
        type: boolean
        default: false

jobs:
  bump-and-release:
    uses: your-org/release-workflows/.github/workflows/bumpver-release.yml@v1
    with:
      level: ${{ github.event.inputs.level }}
      use_ai_release_notes: ${{ github.event.inputs.use_ai_release_notes }}
      update_changelog: ${{ github.event.inputs.update_changelog }}
    secrets:
      OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
```

Your project must configure `pyproject.toml` with bumpver, for example:

```toml
[project]
version = "0.1.0"

[tool.bumpver]
current_version = "0.1.0"
version_pattern = "MAJOR.MINOR.PATCH"

[tool.bumpver.file_patterns]
"pyproject.toml" = ['version = "{version}"']
```

## Choosing a model

With `use_ai_release_notes: true`, the notes are written by `gpt-6-astra`
unless something else is configured. There are two ways to change that, and
they compose:

- Set the repository (or organization) Actions variable `OPENAI_MODEL` in the
  **calling** repository. The workflow reads it with `vars`, which resolves
  against the caller, so every release that calls this workflow follows it with
  no workflow edit.
- Pass the optional `model` input for a single call. It wins over the variable
  when nonempty, and leaving it unset falls back to the variable, then to the
  default.

```yaml
jobs:
  bump-and-release:
    uses: your-org/release-workflows/.github/workflows/bumpver-release.yml@v1
    with:
      level: patch
      use_ai_release_notes: true
      # Omit this line to follow the OPENAI_MODEL repository variable.
      model: gpt-5.6-sol
    secrets:
      OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
```

Setting `OPENAI_MODEL` in an `env:` block of your caller workflow does **not**
work: GitHub does not propagate a caller's workflow-level environment into a
called workflow. Use the input or the variable. See
[Choosing an OpenAI model](https://github.com/everydaydevopsio/castoff/blob/main/docs/model-selection.md)
for the full precedence rules and how to confirm which model a release used.

## Changelog entries

Set `update_changelog: true` (with `use_ai_release_notes: true`) to record each
release in `CHANGELOG.md`. The workflow passes the action's `changelog_entry`
output to the [changelog action](https://github.com/everydaydevopsio/castoff/blob/main/changelog/README.md),
then commits the result.

Two things to know:

- The tag is pushed before the notes are generated, so the entry lands as a
  follow-up `docs: update changelog for vX.Y.Z` commit. The tagged commit itself
  does not contain the entry. Castoff's own
  [release workflow](https://github.com/everydaydevopsio/castoff/blob/main/.github/workflows/release.yml)
  generates notes before tagging, so it can amend instead.
- The changelog action creates `CHANGELOG.md` when it is absent, inserts each
  entry below an `## [Unreleased]` section when one exists, and reports
  `updated: false` when the version is already documented, so rerunning a release
  is safe and commits nothing.

This requires Castoff v2.2.0 or later, which publishes the changelog action.

## With and without AI notes

`use_ai_release_notes` picks which of two release-body steps runs. Both always
exist in the workflow; only one produces the release.

### Without AI (the default)

```yaml
jobs:
  bump-and-release:
    uses: your-org/release-workflows/.github/workflows/bumpver-release.yml@v1
    with:
      level: patch
```

No OpenAI key, no secret to pass, no network call. The release body is
GitHub's own autogenerated list of merged pull requests. Use this when commit
subjects are already the changelog you want, or when a key is not available —
pull requests from forks get no secrets, so a fork-triggered release lands here.

### With AI

```yaml
jobs:
  bump-and-release:
    uses: your-org/release-workflows/.github/workflows/bumpver-release.yml@v1
    with:
      level: patch
      use_ai_release_notes: true
      update_changelog: true
    secrets:
      OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
```

Commits are summarized into `## Highlights`, `## Fixes` and `## Changes`, and
`update_changelog: true` records the same notes in `CHANGELOG.md`.

### What differs

|                    | Without AI                           | With AI                            |
| ------------------ | ------------------------------------ | ---------------------------------- |
| Release body       | GitHub's autogenerated PR list       | Grouped prose under three headings |
| Secrets            | none                                 | `OPENAI_API_KEY`                   |
| Cost and latency   | none                                 | one OpenAI call per release        |
| `update_changelog` | ignored — there is no entry to write | writes `CHANGELOG.md`              |
| Determinism        | same input, same output              | wording varies between runs        |

Two behaviors worth knowing:

- **AI failure is not release failure.** If the notes step fails — bad key, quota,
  an API outage — the fallback release step still publishes, with GitHub's
  autogenerated notes. You get a release either way.
- **`update_changelog` needs `use_ai_release_notes`.** The entry comes from the
  generator's `changelog_entry` output, so with AI off there is nothing to
  insert and the changelog steps are skipped.

Start without AI, turn it on once the release flow itself is proven.

Tag your copy (e.g. `v1`) and reference that tag from callers.
