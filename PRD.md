# Product Requirements Document (PRD)

## Product
AI Release Notes GitHub Action (`castoff`)

## Status
Draft v1 (based on current README + code behavior)

## 1. Problem Statement
Engineering teams spend time manually writing release notes from commit history. Existing autogenerated notes are often noisy and not grouped by user-facing value. Teams need consistent, readable release notes with minimal manual effort in CI/CD workflows.

## 2. Product Overview
`castoff` is a GitHub Action that generates Markdown release notes using OpenAI models. It gathers recent commit messages from git history, prompts a model to summarize them into structured sections, and exposes the result as an action output consumable by release workflows.

## 3. Target Users
- Maintainers of GitHub repositories shipping frequent releases
- Teams using release automation workflows (Node/Python examples in this repo)
- Developers who want higher-quality notes than raw commit logs

## 4. Goals
- Generate release notes automatically in CI with minimal setup
- Produce clean Markdown suitable for GitHub Releases
- Keep behavior deterministic and easy to integrate via standard action inputs/outputs
- Support a safe fallback path when AI output is unavailable

## 5. Non-Goals
- Auto-publishing releases directly (handled by downstream release actions/workflows)
- Full semantic analysis of code diffs (input is commit subject lines)
- Multi-language localization of release notes
- Changelog file management in repository files

## 6. User Stories
1. As a maintainer, I can provide my release tag and OpenAI API key to get release notes text as workflow output.
2. As a release engineer, I can choose an OpenAI model without editing action code.
3. As a workflow author, I can limit commit volume to control token/cost usage.
4. As a maintainer, I receive a fallback note body if AI response content is missing.

## 7. Functional Requirements

### 7.1 Inputs
- `openai_api_key` (required): API key used to call OpenAI.
- `tag` (required): Release tag string for prompt context and fallback title.
- `model` (optional, default `gpt-4.1-mini`): OpenAI model name.
- `max_commits` (optional, default `200`): Max number of commits read from git log.

### 7.2 Output
- `release_notes`: Markdown string suitable for use as GitHub Release body.

### 7.3 Commit Range and Collection
- Action attempts to detect previous tag via `git describe --tags --abbrev=0 HEAD^`.
- If previous tag exists, commit range is `<previousTag>..HEAD`.
- If no previous tag is found, range is `HEAD` and action logs informational message.
- Commit messages are read using `git log --pretty=format:'%h %s' ... -n <max_commits>`.
- Empty or whitespace lines are filtered; non-empty commits are formatted as bullet list entries.

### 7.4 Prompting Behavior
- Prompt includes current release tag.
- Prompt includes previous tag (or `None`).
- Prompt includes commit bullet list (or `_No commits found_`).
- Prompt includes formatting requirements for `## Highlights`, `## Fixes`, and `## Changes`.
- Action sends a system message positioning model as an expert technical writer.
- Action sends a user message containing the generated prompt.
- OpenAI request temperature is `0.4`.

### 7.5 Success and Failure Behavior
- On successful completion, action sets `release_notes` output and logs success message.
- If OpenAI response content is empty/missing, action returns fallback heading `# Release <tag>`.
- If OpenAI response content is empty/missing, action returns fallback text `_Auto-generated notes unavailable._`.
- On runtime error (input issues, git failure, API failure, etc.), action fails using `core.setFailed(error.message)`.

## 8. Non-Functional Requirements
- Runtime compatibility: GitHub Actions Node.js 20.
- Reliability: Must fail fast with clear error on unrecoverable runtime exceptions.
- Security: OpenAI key provided via Actions secrets; action must not print key.
- Performance: Should complete within typical workflow step timeouts for <=200 commits.
- Maintainability: Core logic remains testable via exported pure helpers (`formatCommits`, `buildPrompt`, `extractNotes`).

## 9. UX and Integration Requirements
- Setup should require only one action step plus release step wiring.
- Output must be directly consumable by `softprops/action-gh-release` `body` input.
- Documentation should include minimal usage and fallback strategy.

## 10. Metrics and Success Criteria
- Adoption: Number of workflows invoking the action (downstream signal).
- Quality proxy: Maintainer-reported reduction in manual release-note editing.
- Reliability metric: Action success rate in CI runs.
- Reliability metric: Percentage of runs producing non-fallback AI content.
- Cost control: Commit cap usage via `max_commits`.

## 11. Constraints and Dependencies
- Requires git history/tags availability in workflow checkout.
- Requires valid OpenAI API key and network access to OpenAI API.
- Output quality depends on commit message quality and structure.
- Token/cost footprint scales with commit volume and message length.

## 12. Risks
- Poor commit hygiene can degrade summary quality.
- Missing tag history or shallow clones may reduce context.
- Model output variability may produce inconsistent section balance.
- API outages or quota limits can fail the action.

## 13. Assumptions
- Repositories follow tag-based release workflows.
- Commit subjects provide enough signal for meaningful summaries.
- Consumers prefer concise human-readable summaries over exhaustive logs.

## 14. Acceptance Criteria (v1)
1. Given required inputs, action emits non-empty `release_notes` output.
2. For repos with no previous tag, action still runs and includes `Previous tag: None` context.
3. For empty OpenAI content, fallback markdown is returned with the provided tag.
4. In release workflow usage, output can be passed directly as GitHub Release body.
5. Unit tests for helper functions pass for formatting, prompt construction, and extraction fallback behavior.

## 15. Deployment Pipeline

### 15.1 Artifact Model
- Action is distributed as a bundled `dist/index.js` compiled by `@vercel/ncc`.
- `action.yml` references `dist/index.js` (not `index.js`) so consumers do not need `node_modules/`.
- `dist/` is committed into git as part of each release commit.

### 15.2 Release Workflow (`.github/workflows/release.yml`)
- Triggered manually via `workflow_dispatch` with `level` input (`patch` | `minor` | `major`).
- Steps in order:
  1. Run full test suite — fail fast if tests do not pass.
  2. Bump `package.json` version via `npm version <level> --no-git-tag-version`.
  3. Compile `dist/index.js` via `pnpm build` (ncc).
  4. Commit `package.json` and `dist/` with message `chore: release vX.Y.Z`.
  5. Create an exact version tag (`vX.Y.Z`) and update the floating major tag (`vN`) in place.
  6. Push all tags and the commit to `main`.
  7. Optionally generate AI release notes using the action itself (`OPENAI_API_KEY` secret required).
  8. Create a GitHub Release for `vX.Y.Z` with AI notes or GitHub-autogenerated notes as fallback.

### 15.3 CI Workflow (`.github/workflows/ci.yml`)
- Triggered on push and pull requests to `main`.
- Jobs: `test` (jest with coverage ≥ 75%) and `lint` (ESLint + Prettier check).
- Uses concurrency cancel-in-progress to avoid redundant runs.

### 15.4 Consumer Usage
Users reference the action by major version tag:
```yaml
uses: everydaydevopsio/castoff/castoff@v0
```
Or by exact version for pinning:
```yaml
uses: everydaydevopsio/castoff/castoff@v0.1.0
```

## 16. Future Enhancements (Post-v1)
- Configurable prompt templates and section headings.
- Optional inclusion of PR titles, labels, or conventional-commit grouping.
- Built-in retry/backoff on transient API errors.
- Optional style profiles (short, detailed, user-facing, technical).
- Repository-specific instructions input for tone and structure.
